# 云化迁移计划

## 目标架构

- 小程序前端：`Uni-app`
- 后端服务：`Google Cloud Run`
- 数据库：`Neon PostgreSQL`
- 对象存储：`Cloudflare R2`

## 当前已完成

### 后端骨架

- `Express` 服务已完成初始化
- `Prisma schema` 已落地
- `Dockerfile` 已可用于 Cloud Run 构建
- 认证、租户、房源、房间、附件、导出路由已建立

### 已接通的后端能力

- 微信登录骨架
- 多租户上下文
- 院落结构读取
- 房间详情读取
- 办理入住
- 房租收费
- 附加收费
- 抄表生成费用
- 退租
- R2 预签名上传
- 附件确认入库
- 导出任务生成与历史查询

### 前端已接通的云端链路

- 登录 / 当前租户恢复
- 院落树读取
- 房间详情读取
- 办理入住
- 房租收费
- 附加收费
- 抄表
- 退租
- 身份证 / 合同 / 房屋照片 / 收费凭证 / 抄表照片上传
- 云端导出任务与导出历史

## 迁移顺序

### 第一阶段：云服务落地

1. 建 Neon 数据库
2. 建 R2 Bucket 和访问域名
3. 配 Cloud Run 服务
4. 配环境变量和密钥
5. 运行 Prisma 迁移

### 第二阶段：前端切主链路

1. 登录 / 租户
2. 院落结构读取
3. 房间详情读取
4. 办理入住
5. 收租 / 收附加费 / 抄表 / 退租
6. 附件上传
7. 导出

### 第三阶段：削弱本地状态

1. 将 `rentStore` 从主数据源降为缓存层
2. 保留最小必要 fallback
3. 清理重复的本地写逻辑

## 风险提示

1. 小程序访问 Cloud Run / R2 必须使用正式域名，不建议直接暴露原始平台域名
2. 所有业务表必须带 `tenantId`
3. R2 当前只完成上传链路，下载鉴权和生命周期还未完成
4. 现阶段仍是“云端优先 + 本地 fallback”，不是真正单一数据源
